# Runtime deployment configuration

This is source configuration, not a production authorization or commercial-readiness claim. Use a dedicated PostgreSQL cluster and a backup/restore plan. Set the placeholders in `.env.example` through the deployment secret store; URLs must use `postgres` and distinct maintenance and restricted runtime credentials. The maintenance user must be able to create extensions and roles. The runtime password must be at least 16 characters and the login name must be lowercase ASCII letters/digits/underscores, starting with a letter. Never reuse a privileged or object-owning role. Provisioning will not adopt pre-existing logins; choose a new dedicated name. Subsequent runs only accept a login created and marked by this runner. `APP_VERSION` should be the exact source commit SHA.

Coolify must support Compose build contexts, health-based `depends_on`, and a completed one-shot service. Route the reverse proxy to `web:3000` on the Compose edge network; configure the actual domain and TLS in Coolify. No database/cache ports are published. The edge network permits outbound provider access; do not publicly route API, worker or health endpoints without an explicit access policy. The cache is private and ephemeral. On each release, ensure the migration job is recreated and succeeds against the new image before application services start. If the platform cannot honor migration completion ordering, run and verify the migration job before starting application services. No Docker socket is required.

The migration job checks SHA-256 for newly recorded files under a PostgreSQL advisory lock, rejects missing/changed recorded files, and applies each migration transactionally. Existing rows without checksums are reported as `historicalUnverified`: their past content cannot be verified and is deliberately not backfilled. Review them against trusted backups separately. Migration 0001 and 0007 affect the cluster-wide `vaarg_app` role, and 0007 disables its login/password. Fresh installations precreate this group NOLOGIN to avoid the historical fixed password. On existing clusters review all databases and provision compatible restricted logins before upgrading; explicitly set `MIGRATION_ALLOW_CLUSTER_ROLE_CHANGE=true` only after that review. Never share this cluster-wide group across unrelated deployments. Migration role credentials are available only to PostgreSQL and the one-shot job. Rotation of runtime credentials requires coordinated service recreation. PostgreSQL statement logging can expose role password SQL: protect/disable such logging for provisioning. Do not log environment variables or connection URLs.

Compose healthchecks describe process and dependency connectivity, not Shopify access, worker transport, data correctness or commercial readiness. Worker has no Hatchet consumer. Storefront bindings are optional; when configured, this Compose exposes only `SHOPIFY_STOREFRONT_TOKEN` as the named token variable; customize the explicit secret mappings for multiple stores. Startup/redeploy must retain `vaarg_pg_prod`; `down` does not delete it. The explicit `db:reset:dev` deletes only the development Compose volume. Do not run destructive resets against production. Docker builds, upgrades, failure recovery, TLS/proxy and restored backups require real local certification before deployment.
